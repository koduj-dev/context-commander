# 0019. Browser authentication: sessions, local passwords, and directory identity

## Status

Accepted

## Context

A fresh installation cannot be opened. The web UI's only sign-in is "paste a
PAT" (`web/src/pages/SignIn.tsx`), and the only way to obtain a PAT is
`ccd token create` on the machine that runs the server. So the documented
first-run experience for a self-hosted product is: install it, then get a
shell on the host and run a CLI before anyone can look at it. The maintainer
named this directly on 2026-10-06 — *"to create that PAT I first need ccd itself —
which defeats the point"* — and it is the same chicken-and-egg ADR 0009 solved for
the API and never solved for the browser.

Two further gaps make this one decision rather than three. The deployment the
maintainer describes is a company installing this and handing out access
authorized through OAuth or LDAP, with agents connecting over MCP
(`NEXT.md` Phase 3). Nothing of that exists: there is one credential type, it
is a bearer token, and `users` has no password, no external subject and no
notion of where a person's identity came from. And the UI is already written
against the gap — the sign-in screen explains the CLI command, which is a
product telling its user to go elsewhere.

What must not be disturbed: `identity.Authenticate` is the single chokepoint
every adapter shares (ADR 0009), PATs stay exactly as they are because agents
and the CLI depend on them, and the API keeps speaking one machine format to
its other reader, a model (NEXT.md, "Localization is a UI concern").

## Decision

### A browser session is a credential row, not a new mechanism

A session is a row in `client_credentials` with `client_type = 'session'` and
a non-null `expires_at`. The token is generated by `identity.GenerateToken`,
verified by `identity.Authenticate`, revoked by the row's `revoked_at`, and
rate-limited by the limiter already keyed on credential id. No second
verification path, no second revocation story, no second place for an "is
this still valid" bug to live.

The consequences are deliberate, not incidental: a stolen session dies on
revocation like any other credential; `last_used_at` already tells a user
which of their sessions is live; and the security log already records every
failure against it. The one thing it needs is a filter — the personal access
token screen must not list sessions as tokens, and the new sessions screen
must not list tokens as sessions. `client_type` is free text today and stays
free text; only these two readers interpret it.

### The session token travels in an HttpOnly cookie, never in JavaScript

`Set-Cookie: cc_session=…; HttpOnly; SameSite=Lax; Path=/`, plus `Secure`
unless the operator passed `--insecure-allow-cleartext`. Today the UI keeps a
PAT in `localStorage`, which was defensible while the only credential was one
the user pasted by hand and could revoke. It stops being defensible the moment
a password creates the credential: any XSS in the SPA would lift a long-lived
token out of storage, and the user would have no idea it happened. A cookie
the page cannot read removes that whole class.

**CSRF**: cookie authentication is accepted only on requests carrying
`X-Requested-With: cc-web`. A cross-site HTML form cannot set a custom header,
and a cross-origin XHR that tries is stopped by the preflight, because no CORS
middleware exists and the SPA is served from the same origin as the API by the
same binary. `SameSite=Lax` is the second layer, not the only one. Bearer
tokens are unaffected: a PAT in an `Authorization` header is not sent by a
browser on anyone else's behalf.

### Local passwords live in their own table, hashed with argon2id

`user_passwords(user_id PK, password_hash, algorithm, updated_at)` — a
separate table rather than a column on `users`, so a person who authenticates
only through a directory has no row at all. "Has a local password" is then a
fact that can be seen rather than inferred from a NULL, and revoking local
login for a directory-managed account is a delete rather than a flag.

argon2id (`golang.org/x/crypto/argon2`, already in the module graph),
m=64MiB t=3 p=4, stored in PHC string format so the parameters travel with the
hash and can be raised later without a migration. This is the opposite choice
from `HashSecret`'s SHA-256 for PATs, and both are right: a 256-bit random
secret does not need a slow hash, and a human-chosen password needs nothing
else.

Password authentication is rate-limited per identifier, not only per
credential — a credential id is what you get *after* a successful login, so
the existing limiter cannot see a brute-force attempt at all. A failed attempt
costs the same wall-clock time whether or not the account exists: the verify
runs against a dummy hash when the lookup misses, so the response time is not
an account enumeration oracle.

### First run is a one-time code printed to the server log

When `users` is empty, `ccd serve` generates a 32-hex-character setup code,
holds it **in memory only**, and prints it as a startup log line. `POST
/v1/setup` accepts that code once and creates the first user, its principal,
its installation-admin grant and its password in one transaction.

In memory rather than in a table: a code in the database survives a restart,
appears in every backup, and outlives its purpose. This one dies with the
process and is reprinted by the next start, which is the correct lifetime for
a credential whose only job is to prove that whoever is calling can read the
server's own output. The honest statement of what it assumes: anyone who can
read the log of a freshly installed instance is already trusted with it. That
is strictly stronger than the alternative of "the first person to reach the
screen becomes admin", and strictly weaker than requiring host shell access —
which is the thing being fixed.

`GET /v1/setup/status` answers whether setup is still needed, so the UI can
route to it without guessing. It leaks exactly one bit — that an installation
has no users — about an instance that has no users to protect yet.

### Directory identity: one mapping table, two providers, same shape

`user_identities(provider, subject, user_id, created_at, PRIMARY KEY
(provider, subject))` maps an external identity to a local user. Both LDAP and
OIDC resolve to this: authenticate against the directory, look up
`(provider, subject)`, create the `users` row and the mapping on first success
(just-in-time provisioning), then issue a session exactly as a password login
would. Everything after the identity is established is shared code.

The subject is the directory's stable identifier — `entryUUID` for LDAP, the
`sub` claim for OIDC — never the email address. An email is a label a person
can change and an administrator can reassign; treating it as the key is how
one person inherits another's projects.

**OIDC, not SAML.** Authorization code flow with PKCE and discovery
(`.well-known/openid-configuration`), which covers Entra ID, Google, Okta,
Keycloak, Authentik and GitLab from one implementation. SAML is deliberately
out of scope: it is a second protocol, with XML signature verification as its
security-critical core, for a set of deployments this product does not have
yet. If one appears, it is another ADR.

**Roles are not read from the directory.** A successful directory
authentication proves who someone is, not what they may do. Authorization
stays where ADR 0014 and ADR 0017 put it: project membership, organization
membership and `installation_admins`. Group-to-role mapping is a real feature
and it is a separate decision from logging in.

### What the sign-in screen may offer, the server decides

`GET /v1/auth/methods` returns which methods are configured — password, LDAP,
and each OIDC provider by display name. The UI renders that list and nothing
else, which is the design rule it already has ("never fake a capability the
backend lacks", `.claude/skills/ui-design/SKILL.md`) applied to the one screen
that was breaking it.

## Consequences

- PATs are untouched. Agents, the CLI and MCP keep working exactly as before,
  and the PAT path stays available in the browser as a secondary method for an
  operator who has one and no password yet.
- Sessions and PATs share a table, so every future question about credentials
  — expiry, revocation, listing, auditing — is answered once.
- `golang.org/x/crypto` and `golang.org/x/oauth2` move from indirect to direct
  dependencies. LDAP and OIDC each add one library; neither is needed for the
  password path to ship.
- A browser now holds a credential the page cannot read, so the UI can no
  longer attach a token itself: `web/src/lib/api.ts` sends the cookie and the
  CSRF header, and keeps the bearer path only for the PAT method.
- An installation with a directory configured can still create local
  passwords. Forbidding that is a configuration decision, and the table shape
  above makes it a policy over rows that exist rather than a schema change.
