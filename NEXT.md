## 🎯 What we want from it

A self-hosted, vendor-neutral shared context and collaboration layer for humans
and AI agents: a common project-scoped workspace to store artifacts, preserve
context, hand work between agents, share skills, and publish events — with
project-level RBAC and no dependency on any single AI vendor. See the cookbook
§1 for the full definition.

The design (cookbook + 16 ADRs) is mostly settled. The gap right now is between
*designed* and *built*.

## 🔭 Open work

### Domain packages that are still just a stub

These live under `internal/` as a bare `doc.go` today — the cookbook chapter
designed the model, nothing implements it yet:

- **Handoffs** (cookbook §9) — the structured "current handoff" record (task,
  completed, artifacts, next) that lets one agent pick up cleanly where
  another left off.
- **History / session lineage** (§10) — providers' own session IDs are not
  stable conversation identities (§10.1); CC needs its own lineage model
  (§10.2) where compaction never overwrites original history (§10.3), and
  lineage isn't assumed to be a single tree (§10.4).
- **Skill Registry** (§12, ADR 0012) — `SkillVersion` (immutable package) vs.
  `SkillBinding` (installation), publish/pin/override semantics, and the
  client-side `ccd sync-skills` that actually writes `.claude/skills/` (the
  server never touches a client's filesystem).
- **Gates** (§13.2) — distinct from Skills: guidance vs. enforcement (§13.3).
- **Secrets** — project metadata for external integrations (§5.4); the
  encryption/classification model exists (ADR 0011) but the domain package
  doesn't.

### Partially built

- **Events** (`internal/events`, 80 lines) — types exist; no delivery
  mechanism yet. §11.1/§11.2 designed this as transport-agnostic and
  deliberately *not* implying agent wake-up on notification — worth
  re-reading before wiring a transport so that constraint survives.
- **Organizations** (`internal/organizations`, 101 lines) — ADR 0006 decided
  org-vs-project authorization; check what's actually enforced today against
  what the ADR promises before calling this done.
- **Audit** (`internal/audit`, 51 lines) — minimal today; docker-commander's
  `docs/audit.md` is a reasonable shape reference for what a complete audit
  story covers (what's recorded, retention, who can read it).

### Adapter catch-up

`adapters/mcp` and `adapters/http` (Phase 4) only expose **project** and
**artifact** operations so far. Every domain above needs the same adapter
treatment once built — MCP tools + HTTP routes + CLI, mirroring the
project/artifact pattern already established.

### Packaging and distribution

- [x] OS packaging scaffolding (`deploy/nfpm.yaml`, `deploy/packaging/`) —
  added, adapted (not copied verbatim) from docker-commander: no config-file
  loader yet, so `ccd.service` reads `/etc/context-commander/ccd.env`
  instead of a `commander.conf`-style file; `CC_ROOT_KEY` can't be
  autogenerated safely, so `postinstall.sh` creates the env file empty and
  tells the operator what to set. **Not yet wired to a release workflow** —
  no `release.yml`/`.github/workflows` builds or publishes these packages,
  and there's no man page. Revisit once CC is near a shippable state.

## 🗺️ Working priority order

**Proposed 2026-08-28 — not yet confirmed with the maintainer.** Reasoning
below; check items off as they ship, revisit deliberately if it turns out
wrong, don't just silently reshuffle it.

**Now — one bundle (Handoffs is the reason Events needs a real transport):**
- [ ] Handoffs (§9) — the most identity-defining piece not yet built: the
  cookbook's own one-sentence definition names "hand work over to another
  agent" explicitly, and it's self-contained enough to mirror the
  project/artifact adapter pattern (domain service → MCP tools → HTTP routes
  → CLI) that Phase 4 already established.
- [ ] Events (§11) — 80 lines of types with no delivery mechanism is dead
  weight until something needs notifying about. A handoff landing is the
  first concrete thing worth that; keep it a read/poll surface, not a push
  one — §11.2 is explicit that notification must not imply agent wake-up.

**Next, each standalone:**
- [ ] History / session lineage (§10) — conceptually follows Handoffs (an
  agent resuming one needs to know which session it's continuing) but is a
  big enough model on its own (provider session IDs aren't stable identities,
  compaction must not overwrite original history, lineage isn't always a
  tree) to be its own item, not a sub-task of Handoffs.
- [ ] Organizations hardening — close the gap between what ADR 0006 promises
  and what `internal/organizations` actually enforces. Hardening existing
  surface, not new domain, but worth doing before Skills/Gates below start
  leaning on org-level RBAC being trustworthy.
- [ ] Audit expansion — `internal/audit` is minimal (51 lines); give it
  something real to record once Handoffs/Events exist, then decide retention
  and who-can-read the way docker-commander's `docs/audit.md` frames it.

**Bigger, separately scoped:**
- [ ] Skill Registry (§12, ADR 0012) — fully specified already (publish vs.
  binding, pin/override, client-side `ccd sync-skills`); big enough to be its
  own phase rather than folded into something else.
- [ ] Gates (§13) — depends on Skills existing first: the guidance-vs-
  enforcement distinction in §13.3 only makes sense once there's a Skill to
  contrast a Gate against.
- [ ] Secrets — project metadata for external integrations (§5.4); not
  blocking anything internal today, matters once a real external integration
  (git-bound projects, etc.) needs a credential that isn't a root key.

**Trailing, lower urgency:**
- [ ] Adapter catch-up (MCP/HTTP/CLI for each domain above) — not its own
  phase, happens alongside each domain as it's built.
- [ ] `docs/testing.md`, `docs/README.md` manual index — once there's enough
  surface to actually describe/link.
- [ ] Packaging release wiring (`release.yml`, man page) — once CC is near a
  shippable state; the scaffolding itself already exists (see above).
